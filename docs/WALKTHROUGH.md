# Маршрут разбора проекта

Этот файл помогает изучить реализацию и проверить понимание на работающей программе.
Начните с маленьких примеров, предсказывайте следующий шаг, затем сверяйтесь с трассой.

## 1. Карточки и команды

Возьмите `[3 1 2]` и пустой B. Что сделают `ra`, `rra`, `pb`? Как изменится
результат, если перед `pa` стек B пуст? Проверьте через `checker`:

```sh
printf 'ra\n' | ./checker "3 1 2"
printf 'pb\n' | ./checker "3 1 2"
```

Прочитайте `internal/operations/operations.go`. Здесь нет выбора стратегии —
только точный смысл команд. Затем откройте `internal/stack/stack.go`: `head`
обозначает начало кольца, `size` — количество занятых мест. Почему смена верхушки
не требует сдвигать все элементы массива?

## 2. Маленький список

```sh
./ai-coach debug "5 1 4 2 3"
```

Сначала предложите своё решение на бумаге. После запуска посчитайте команды.
Посмотрите `exact.go`: очередь сначала обрабатывает ближние состояния, затем
дальние. Объясните своими словами, почему найденный путь кратчайший и почему
тот же подход неудобен для 100 значений.

Смените числа на `50 10 40 20 30`. Порядок команд должен совпасть: важны ранги.

## 3. Сравнение алгоритмов

```sh
./ai-coach compare "$(cat testdata/test_medium.txt)"
```

Разберите отличие **измеренного числа команд**, **верхней оценки сложности**
и **глобального минимума**. Почему одинаковое направление вращения двух стеков
можно оплатить один раз? Найдите расчёт цены в `greedy.go`.

Попробуйте reverse, циклический сдвиг и случайную перестановку. Ни один единичный
пример сам по себе не доказывает качество алгоритма на всех входах.

## 4. Запрос к модели

Пройдите цепочку `cli.AICoach` → `Coach.Run` → `prompt` → `Client.Complete`.
В ней режимы задают вопрос, промпт собирает доказательства, клиент отвечает за HTTP.

Ответьте на вопросы:

1. Где задаются адрес, имя модели и ключ? Отправляется ли пустой ключ?
2. Что содержит поле `messages`? Где хранится история чата?
3. Что происходит через 10 секунд без ответа?
4. Почему текст от модели не может исправить результат `checker`?
5. Как проверить ошибочную ветку debug, если обычный сортировщик работает правильно?

Для последнего вопроса прочитайте `TestDebugFailureSuppliesFullTraceAndFix`:
тест подставляет неисправный планировщик и наблюдает настоящий запрос.

## 5. Самостоятельное изменение с проверкой

Измените ширину одной группы рангов, запустите `make stress` и сравните среднее
и максимум. Затем верните изменение или добавьте обоснованную новую стратегию.
Сначала запишите ожидаемое поведение и новый тест, затем проверьте реальные числа.

Военная дисциплина и многолетняя утренняя практика здесь выражаются в повторяемом
цикле: понять действие, выполнить, проверить, исправить и повторить. Техническое
решение становится собственным навыком, когда его можно объяснить и изменить.
